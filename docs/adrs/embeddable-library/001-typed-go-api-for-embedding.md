# gcx as an embeddable Go library: typed API, not a CLI shim

**Created**: 2026-09-11
**Status**: proposed
**Supersedes**: none

## Context

The Grafana MCP server (mcp-grafana) wants to offer things gcx already knows how to do — SLO, Synthetic Monitoring, Fleet Management, and more — without writing its own REST client for each of those products from scratch. That's not a hypothetical want: SLO, Synthetic Monitoring, and k6 don't exist at all in mcp-grafana today. mcp-grafana already does this for a couple of other products by importing a ready-made Go library instead of hand-rolling a client — it uses `amixr-api-go-client` for OnCall and `incident-go` for IRM. We want gcx's other products to work the same way: something you can `import` and call, not something you have to talk to over a wire protocol you build yourself.

There's already an open, unreviewed pull request (gcx#558) that tried to solve this a different way. It added a function, `gcxlib.Execute(ctx, args, config)`, that runs gcx *as if from the command line*, in the same process: you hand it a list of strings like `["alert", "rules", "list"]`, and you get back whatever gcx would have printed to stdout, as JSON text. Looking closely at that approach turned up three real problems:

1. **Auth leaks through the cracks.** gcx has more than one internal place that decides "where do I get my Grafana credentials from." PR #558 patches two of them so they'll accept credentials handed to them programmatically instead of reading them from a config file on disk — and its own commit history shows it missed the second one on the first try. There's a third one, used by k6, Synthetic Monitoring's first-time setup, Faro's sourcemap upload, and Adaptive Telemetry, that still isn't patched at all. Anyone using that shim for those features would silently fall back to reading a config file that doesn't exist in an embedded program — and just fail, or worse, pick up whatever leftover config happens to be lying around on the host machine.
2. **It leans on global, mutable settings.** Every call to `Execute()` flips several settings that live outside any single request — things like "are we in agent mode," "is color output on." Right now every call happens to set them to the same values, so nothing's broken yet. But mcp-grafana genuinely runs multiple requests at the same time in the same process, so relying on "it happens to always agree with itself" is asking for a bug that only shows up under load.
3. **It doesn't actually save the work it promises to.** The whole pitch is "don't write a client for every product." But with this shim, mcp-grafana still has to know the exact command-line arguments for every operation and how to parse gcx's JSON output for every operation — it's a thinner client, not zero client.

Separately, mcp-grafana already handles multiple Grafana instances and users within one running server — each request carries its own URL, token, and org ID, pulled from HTTP headers. And mcp-grafana deliberately avoided using the standard Kubernetes Go library (`k8s.io/client-go`) for talking to Grafana's newer Kubernetes-style APIs, writing a much smaller hand-rolled version instead, specifically to keep its own dependency list light. gcx's dashboard/folder code does use `client-go` directly.

There is a third consumer, and it is not hypothetical either: `grafana-assistant-app`. It is an internal, polyglot monorepo with seven Go modules, and it already hand-rolls the very clients this library is meant to provide — SLO against the identical plugin path gcx uses, a complete IRM client of its own, and raw HTTP to the alerting provisioning API. It also already imports mcp-grafana as a Go library. So the same product clients exist in three places today, not two, and one of those three is a repo that public repos cannot depend on in return.

That raises a question this ADR has to answer alongside the API shape: how should these repos be organised so the library can be maintained over time without chaining pull requests across repos every time something needs to ship? The honest constraint is that full atomicity — one pull request changing the library and every consumer together — is only available inside a single repository, and `grafana-assistant-app` is internal while gcx and mcp-grafana are public, so it can never share a repository with them. Whatever we choose, at least one consumer will always be consuming a released version rather than moving in lockstep.

One more thing worth being upfront about: gcx's own foundational documents (the CONSTITUTION, which lists hard rules, and the VISION doc, which describes what gcx is for) don't currently say anything about gcx being usable as a library at all. They're not against it — they just don't mention it, because it wasn't a thing when they were written. VISION.md describes gcx as "a single CLI." That's the gap this decision is meant to close.

## Decision

gcx will offer a **typed Go API** — real functions with real input and output types — rather than the argument-list-in, JSON-text-out shim from PR #558. Each product gcx supports (starting with one, as a pilot) gets its own ordinary, importable Go package with real methods, the same shape as a normal Go SDK.

The specifics:

- **How auth works**: the caller hands over an already-configured `*http.Client` and a base URL. The library does not build its own network transport, does not go looking for a token anywhere, and does not read any config file. Whoever's calling the library is fully responsible for auth — exactly like using `amixr-api-go-client` or `incident-go` today.
- **Where the code lives**: in the gcx repo, but as **its own Go module** — a `client/go.mod` declaring `github.com/grafana/gcx/client`, released with `client/vX.Y.Z` tags. Import paths are unchanged by this (`github.com/grafana/gcx/client/slo` resolves exactly the same either way), so it costs consumers nothing. The point of the separate module is that consumers get only the library's own dependencies — which are the standard library — instead of inheriting everything gcx's CLI needs. This is an established pattern at Grafana rather than a new one: `grafana/loki` ships `operator/go.mod` as `github.com/grafana/loki/operator` with `operator/vX.Y.Z` tags, and `grafana/grafana` releases several modules from one repo the same way.
- **The CLI still dogfoods it**: gcx's own commands switch over to calling the library **immediately**, product by product, as each one is built — never leaving two copies of the same logic (one for the CLI, one for the library) running side by side, even temporarily. Because both live in one repo, that cutover is a single pull request.
- **Version and stability**: the client module carries its own `v0.x` version line, separate from gcx's. Breaking changes are allowed, and consumers pin and bump deliberately. This is a deliberate reversal of an earlier draft of this ADR, which said one module and one version released with the CLI; that only made sense while the library lived inside the gcx module. `v1` is worth considering once anything outside these three consumers depends on it.
- **What shape the packages take**: one package per product (`slo`, `alert`, `kg`, `irm`, `datasources`, and so on), all inside the single `client` module. Five of them now exist, which settles the question an earlier draft deferred: consumers genuinely import subsets, and every package's dependency graph is identical (standard library only), so splitting each product into its own module would buy N version lines and N dependency bumps for no benefit. The one thing that would justify giving a product its own module is it needing a heavy dependency the others should not inherit.
- **How much atomicity this actually buys**: changes spanning the library and the gcx CLI are atomic, because they are one repo and one pull request. mcp-grafana and `grafana-assistant-app` consume published `client/vX.Y.Z` versions instead, which is not atomic and cannot be — the latter is internal and the other two are public, so no single repository can hold them all. We are choosing "atomic where it is achievable" over a monorepo, not claiming atomicity everywhere.
- **Releasing it**: because Go ignores a `replace` directive for anyone downstream, gcx's root module needs a real, published `client` version in its `require` line or `go install .../cmd/gcx@vX` breaks for everyone. So releases are ordered: tag `client/vX.Y.Z`, bump the root `require`, then tag `vA.B.C`. `mise run tag` automates that sequence, so it stays one command. Note what this means: the chaining does not disappear, it moves from between repos into one repo's release script, and it is borne by gcx's own binary release rather than by the library's consumers.
- **Who may add to it**: all three consumers are maintained by the same team, so there is no ownership split to manage. Surface that a consumer genuinely needs may be added even when gcx's own CLI has no use for it — otherwise the library can only ever be as wide as the CLI, and it structurally cannot serve consumers whose needs are broader, which is most of them.
- **How the consumers get there**: mcp-grafana moves from depending on the gcx root module to depending on the client module, and drops the `replace` pins it needed to work around gcx's dependency graph. `grafana-assistant-app` adopts the client library directly, deleting its hand-rolled SLO, IRM and alerting clients — as a follow-up once mcp-grafana has proven the pattern, since it is internal with its own release train. It keeps importing mcp-grafana for MCP hosting, which is a separate concern.
- **What's included by default**: everything, except:
  - Things that only make sense from a terminal: `dev`, `login`, `cloud` (both the "manage Cloud stacks" and "cloud login" pieces), `config`, `setup`, `agent`, `skills`, `commands`, `helptree`, `version`.
  - Things tied to a Grafana Cloud account-level token rather than a single Grafana instance, which doesn't fit "caller hands us an `http.Client`": **k6**, **Faro's sourcemap upload**, **Adaptive Telemetry**, and specifically **Synthetic Monitoring's first-time token setup** (the rest of Synthetic Monitoring is fine and stays in). **Fleet Management is not excluded** — an earlier decision (ADR-023) already moved it off that account-level token onto the same per-instance auth everything else uses.
  - Two commands that can't work without a terminal no matter what: `resources edit` (opens your text editor) and `instrumentation setup` (an interactive yes/no wizard).
  - Two things that get *adjusted*, not dropped: a `--open`-a-browser flag on a few commands just returns the URL instead (it already does this in agent mode today). And commands that currently ask "are you sure? [y/N]" before deleting something (across IRM, alerting, SLO, the knowledge graph, dashboards, Synthetic Monitoring, and app observability) keep that ability in the library — they just take an explicit yes/no parameter instead of reading it from a keyboard, because leaving all of those out would make the library read-only for most products, which defeats the point.
- **Dashboards and folders** keep using `k8s.io/client-go` exactly as they do today. We're not rewriting that part to avoid the dependency.
- **Process going forward**: the checklist for adding a new product to gcx gets updated to require a typed library package and an immediate cutover of that product's CLI commands, as part of the same pull request — not "we'll get to it later."

### What we considered and said no to

- **PR #558's shim.** Rejected: it still leaves mcp-grafana writing a client per command, it depends on global settings that only work by coincidence today, and its auth-handoff mechanism has already needed one bug fix with a second, unfixed gap still open.
- **Keeping the library inside gcx's own module**, as the first draft of this ADR decided. Rejected on evidence: doing it that way made mcp-grafana inherit gcx's entire dependency graph and cost it ten `replace` directives to unbreak code that had nothing to do with anything it imported. The separate module fixes precisely this.
- **A monorepo holding gcx, mcp-grafana and the library together.** This is the only layout that delivers genuinely atomic cross-consumer changes, and it was seriously considered. Rejected because it cannot include the third consumer (`grafana-assistant-app` is internal, the others are public), so it would not actually end cross-repo releases; because moving mcp-grafana changes its Go module path and breaks its documented `go install` line, its MCP-registry identity, which is derived from its repository URL, and its `grafana/mcp-grafana` Docker image name — it has 3,454 stars and 63 releases against gcx's 598 and 30; and because even inside a monorepo, any module consumed as a library still needs ordered, published versions, so the release ordering survives regardless.
- **A brand new, separate repository just for this library.** Rejected: it solves the same dependency problem the separate module solves, while adding a third repo to release and removing the property that makes the CLI dogfood the library in a single pull request.
- **Publishing the library from mcp-grafana instead of gcx**, inverting the dependency. Tempting, because mcp-grafana is already a published Go library that `grafana-assistant-app` imports at a pinned version, so the distribution path is proven. Rejected because mcp-grafana's own dependency graph is heavy (the AWS SDK, Prometheus), gcx's product clients are the richer ones, and it would leave the library's home in the repo whose identity is most expensive to disturb.
- **One Go module per product** (`client/slo/go.mod`, `client/alert/go.mod`, …). Rejected: every one of these packages depends only on the standard library, so per-product modules would multiply version lines, tags and dependency bumps while isolating nothing.
- **Rewriting dashboards/folders to drop the `k8s.io/client-go` dependency**, to match how mcp-grafana avoided it. Rejected — we're exposing what's there today as-is, and letting whoever uses the library decide if they're willing to take on that dependency for that one feature.
- **Figuring out the exact exclusion list later, as we go.** Rejected in favor of naming it up front (the list above), so it doesn't quietly grow every time someone forgets to check.
- **Leaving out every command that currently asks "are you sure?" before deleting something.** Rejected — those commands already behave safely without a terminal (they refuse instead of hanging, unless you pass a flag saying "yes, do it"). Cutting them all would make the library useless for anything beyond reading data.
- **Fixing every place gcx resolves credentials, as a single project, before writing any of this.** Considered, but not necessary right now: since we've already scoped out the features that use the still-unfixed path, and the library's own contract ("you hand us the http.Client") sidesteps the question entirely for everything that is in scope.

## Consequences

**Gets easier:**

- mcp-grafana (and anyone else) gets real access to SLO, Synthetic Monitoring, Fleet, and more, without writing a client for each one from scratch.
- There's never a moment where "what the CLI does" and "what the library does" for the same feature can drift apart — because there's only ever one implementation, and the CLI switches over the same day the library code is written.
- The library doesn't touch any of the settings that only make sense for a terminal (color, "am I in agent mode," etc.) at all — so the concurrency worry that PR #558 had just doesn't apply here; it's not a workaround, the problem doesn't exist in this design.
- It matches a pattern mcp-grafana is already comfortable with (import a typed SDK), instead of asking it to learn a new one.

**Gets harder:**

- This is genuinely new territory for gcx's own rulebook. The CONSTITUTION's rule that business logic belongs only in `internal/`, and the VISION doc's description of gcx as "a single CLI," were both written before this existed, and need updating to say how this new public surface fits in. (Listed as follow-up work below.)
- Code that gets promoted into this public library is, for the first time, making a real promise to people outside the gcx team. The `v0.x` line keeps that promise deliberately weak for now, but the moment a consumer we don't control depends on it, breaking changes stop being cheap.
- Releases are now ordered rather than single-shot: the client module has to be tagged and published before gcx's root `require` can point at it, and therefore before gcx itself can be released. `mise run tag` hides that behind one command, but the ordering is real, and anyone releasing gcx by hand can get it wrong in a way that only shows up when someone runs `go install .../cmd/gcx@vX`.
- A nested module escapes the tooling that assumes one module per repo. `go test ./...` and `golangci-lint run` do not descend into it, so `client/` would silently have no CI at all until the jobs are taught about it; two existing scripts also read git tags unfiltered and would treat `client/v0.1.0` as a gcx version, mis-stamping binaries and generating bogus changelog sections.
- Dashboards/folders still require `k8s.io/client-go`. Anyone who wants that part of the library has to accept that dependency — mcp-grafana specifically chose not to for its own code, so this is a real cost for that one feature, not a clean win everywhere.
- This isn't hypothetical, and we've already seen it happen. Building the first pilot — a `list_slos` tool in mcp-grafana, wired through this library — confirmed it directly. The new `client/slo` package itself only imports `net/http`, `encoding/json`, `context`, `errors`, `fmt`, and `io`, but pulling in gcx as a Go module still pulls in every dependency gcx's own `go.mod` declares, whether `client/slo` uses it or not. Three of those — `grafana-openapi-client-go`, the entire `go.opentelemetry.io/otel` family, and `prometheus/alertmanager` — got bumped to versions that broke existing, working code in mcp-grafana that had nothing to do with SLO at all (a missing model type, an OpenTelemetry schema-version panic, and a downstream compile error, respectively). Getting a clean build required adding ten `replace` directives to mcp-grafana's `go.mod`, pinning each of those back to the version it already had. That's a real, recurring tax on every consumer of this library, not a one-time cost paid once and forgotten — and it will keep happening as gcx's own dependencies move forward, independent of anything the library's own code does. **This is the finding that drove the separate-module decision above**, and it is also the test of whether that decision worked: once `client/` is its own module, those ten pins should largely disappear, because the only thing the consumer imports then depends on is the standard library. If they survive the split, the premise is wrong and worth knowing early.
- **The "don't write it twice" pitch only pays off where gcx's client covers at least as much as the consumer already does.** Converting mcp-grafana tools to this library found that in two of three attempted areas gcx's surface was actually *narrower* than the tool it was meant to replace, so a faithful swap was impossible without extending gcx first. Alerting: mcp-grafana sends nine query parameters to the rules API, six of which `client/alert`'s options can't express (and gcx's `group_limit` is a different parameter from mcp-grafana's `rule_limit`), while its rule type lacks `duration` and `lastError` that the tool's output needs. Incidents: gcx's create-incident request has no `roomPrefix` — which is a *required* parameter on mcp-grafana's `create_incident` tool — nor `attachCaption`/`attachURL`, and `AddActivity` has no `eventTime` and returns nothing to echo back. Datasources: gcx's datasource type has no `id` field, which mcp-grafana's list output exposes. None of these are exotic; they're just the difference between a CLI's needs and an API consumer's. So the real precondition for reuse is not "gcx talks to this product" but "gcx's client is a superset of what the consumer already does", and checking that per area, up front, is now a required step rather than an optimistic assumption. Expect the first conversion of any area to surface gaps that must be filled in gcx before the swap can land.
- Every future product added to gcx now has more required work up front — a library package and an immediate CLI cutover, not just the CLI part. If the checklist doesn't actually enforce this, the exclusion list will quietly grow the same way the unfixed credentials gap did.
- Three copies of these clients exist today (gcx, mcp-grafana, `grafana-assistant-app`), and this decision does not delete two of them by itself — it only makes deleting them possible. Until each consumer actually migrates, the duplication is still there, and now there's a library alongside it.

**Follow-up work this creates:**

- Update VISION.md so it acknowledges gcx as an embeddable library, not only "a single CLI."
- Add a rule to CONSTITUTION.md explaining how this new public Go API relates to the existing "no business logic outside `internal/`" rule and to the CLI's own "stable within a major version" promise.
- Update the provider checklist and the `add-provider` skill so every new product requires a typed library package and CLI cutover, not a follow-up.
- Split `client/` into its own module (`client/go.mod` declaring `github.com/grafana/gcx/client`), and verify the payoff first: check whether mcp-grafana can then drop the ten `replace` pins. That answer decides whether the rest of this work is worth doing.
- Teach the tooling about the second module: extend the existing test and lint jobs to cover it (they use `go test ./...` and `golangci-lint run`, neither of which descends into a nested module), add `client/go.sum` to the CI cache keys, and filter the two tag-reading scripts to `v*` so `client/*` tags stop being mistaken for gcx versions — `mise.toml`'s build task (`git describe --tags --exact-match`) and `scripts/tag.sh`'s changelog backfill. `grafana/loki`'s `operator` module is the closest in-house example to copy from.
- Extend `mise run tag` to do the ordered two-step release (tag the client module, bump the root `require`, tag gcx).
- Migrate the consumers: mcp-grafana from the gcx root module to the client module, then `grafana-assistant-app` directly onto the client library, deleting its hand-rolled SLO, IRM and alerting clients.
- Close the specific surface gaps the mcp-grafana conversions hit, if we want those swaps to land: `client/alert` needs the six missing rules query parameters (`search.folder`, `search.rule_name`, `rule_type`, `rule_limit`, `limit_alerts`, `matcher`), multi-valued state, and `duration`/`lastError` on its rule type; `client/irm` needs `roomPrefix`, `attachCaption` and `attachURL` on create-incident, plus an `eventTime` parameter and a returned activity item on `AddActivity`. Each is additive and evidenced by mcp-grafana's working code, but each also widens gcx's public API for something gcx's own CLI does not use, so they want deciding deliberately rather than by drift.
- Keep an eye on whether dependency-version collisions still reach consumers after the split. They should not, since the client module depends only on the standard library — but if they do, the next thing to consider is a separate repository, because at that point sharing the gcx repo is buying nothing.
